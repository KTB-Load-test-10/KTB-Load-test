# API 부하 테스트 계획서 (로컬 환경)

## 1. 테스트 개요

### 목적
- 백엔드 애플리케이션의 주요 API에 대한 성능 기준점을 확인합니다.
- 부하 발생 시 시스템의 안정성(CPU, 메모리, 응답 시간)을 측정하고 잠재적인 병목 지점을 식별합니다.
- 본 문서는 로컬 환경에서 부하 테스트를 수행하기 위한 절차를 안내하며, 다른 담당자도 이 문서를 보고 동일한 테스트를 재현할 수 있도록 하는 것을 목표로 합니다.

### 범위
- **대상:** REST API (인증, 사용자, 채팅방, 메시지, 파일)
- **제외:** Socket.IO 기반 실시간 메시징 (별도 테스트 계획 수립 예정)
- **환경:** 로컬 개발 환경 (Docker 기반)

---

## 2. 사전 준비 사항

### 필수 도구
1.  **Git:** 프로젝트 코드를 내려받기 위해 필요합니다.
2.  **Java 17 (JDK):** 백엔드 애플리케이션 실행을 위해 필요합니다.
    -   설치되어 있지 않다면, 프로젝트 루트에서 `make setup-java` 명령어로 자동 설치할 수 있습니다.
3.  **Docker & Docker Compose:** 데이터베이스, 모니터링 스택 등 종속 서비스를 실행하기 위해 필수입니다.
4.  **부하 테스트 도구:** 사전에 준비된 부하 테스트 스크립트 실행 도구 (예: k6, JMeter 등).

### 환경 설정
1.  **프로젝트 클론:**
    ```bash
    git clone <저장소_URL>
    cd apps/backend
    ```

2.  **환경 변수 파일 생성:**
    - `.env.template` 파일을 복사하여 `.env` 파일을 생성합니다. 이 파일은 애플리케이션의 주요 설정을 담고 있습니다.
    ```bash
    cp .env.template .env
    ```
    - **중요:** `.env` 파일 내의 `MONGO_URI`, `REDIS_HOST`, `REDIS_PORT` 등 주요 값들은 `make dev` 실행 시 자동으로 설정되므로 별도로 수정할 필요가 없습니다. `JWT_SECRET` 등 비밀 값만 필요시 `make setup-env`로 자동 생성할 수 있습니다.

## 3. 테스트 환경 실행 절차

아래 명령어를 실행하면 백엔드 애플리케이션과 테스트에 필요한 모든 종속 서비스(DB, Redis, 모니터링)가 한번에 실행됩니다.

```bash
make dev
```

실행 후, 아래 주소로 접속하여 각 서비스가 정상적으로 동작하는지 확인합니다.

-   **API 서버:** `http://localhost:5001`
-   **API 문서 (Swagger UI):** `http://localhost:5001/api/swagger-ui.html`
-   **모니터링 대시보드 (Grafana):** `http://localhost:9091` (ID/PW: admin/admin)
-   **메트릭 수집 서버 (Prometheus):** `http://localhost:9090`

> **참고:** 테스트를 중단하고 싶을 때는 `Ctrl + C`를 누르면 모든 서비스가 함께 종료됩니다.

## 4. 테스트 시나리오

부하 테스트는 아래 3가지 핵심 시나리오를 바탕으로 진행합니다. 각 시나리오는 사용자의 실제 이용 흐름을 모방합니다.

### 시나리오 1: 인증 및 사용자 정보 조회
- **흐름:**
    1.  `POST /api/auth/register`: 테스트용 사용자 생성
    2.  `POST /api/auth/login`: 로그인 후 JWT 토큰 획득
    3.  `GET /api/users/me`: 획득한 JWT 토큰으로 내 정보 조회
- **목적:** Stateless하고 가장 빈번하게 호출될 인증 관련 API의 처리량을 측정합니다.

### 시나리오 2: 채팅방 생성 및 메시지 조회
- **흐름:**
    1.  (로그인 후)
    2.  `POST /api/rooms`: 새로운 채팅방 생성
    3.  `GET /api/rooms`: 전체 채팅방 목록 조회
    4.  `GET /api/messages/room/{roomId}`: 특정 채팅방의 이전 메시지 조회
- **목적:** 데이터베이스 읽기/쓰기가 복합적으로 발생하는 핵심 기능의 성능을 측정합니다.

### 시나리오 3: 파일 업로드
- **흐름:**
    1.  (로그인 후)
    2.  `POST /api/files/upload`: 지정된 테스트용 파일(예: 1MB 이미지) 업로드
- **목적:** I/O 집약적인 파일 처리 기능의 성능과 안정성을 측정합니다.

## 5. 부하 테스트 실행 및 결과 측정

### 실행 방법
1.  새로운 터미널을 엽니다.
2.  아래 명령어를 실행하여 준비된 부하 테스트 스크립트를 작동시킵니다.
    ```bash
    # TODO: 여기에 실제 부하 테스트 실행 명령어를 기입해주세요.
    # 예시) k6 run scripts/api_load_test.js
    ```

### 부하 프로필 (예시)
- **가상 사용자(VUs):** 1분 동안 1명에서 50명까지 점진적으로 증가시킨 후, 3분간 50명을 유지하고, 1분 동안 점진적으로 감소시킵니다.
- **총 테스트 시간:** 약 5분

### 중점 모니터링 항목
테스트 실행 중, 아래 항목들을 주의 깊게 관찰하고 결과를 기록해야 합니다.

1.  **부하 테스트 도구 결과 창:**
    -   **`http_req_duration` (p95, p99):** 95%, 99% 사용자의 요청 완료 시간 (응답 시간의 핵심 지표)
    -   **`http_req_failed`:** 전체 요청 중 실패한 요청의 비율 (에러율)
    -   **`iterations` (또는 rps):** 초당 처리량

2.  **Grafana 대시보드 (`http://localhost:9091`):**
    -   **CPU Usage:** 시스템의 CPU 사용률이 100%에 근접하는지 확인합니다.
    -   **JVM Heap Memory:** 메모리 사용량이 지속적으로 증가하여 누수가 의심되는 패턴이 보이는지 확인합니다.
    -   **HTTP Server Requests Latency:** API별 응답 시간이 부하에 따라 어떻게 변하는지 관찰합니다.
    -   **DB Connection Pool:** 사용 가능한 데이터베이스 커넥션이 고갈되는지 확인합니다.
